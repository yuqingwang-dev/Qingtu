# TripPilot 产品定义

## 1. 定位

TripPilot（Personal Travel Copilot）是在现有 Qingtu 应用基础上规划演进的旅行综合智能体。它不以“生成更多目的地推荐”为目标，而是把用户已经想去的地点组织成一套在真实世界中可执行、可解释、可动态调整的行程。

核心价值主张：让行程在时间、空间、预算、体力和实时条件下真正走得通。

## 2. 用户问题

旅行者目前需要在收藏内容、地图、天气、景点官网、餐厅、酒店和交通平台之间反复切换，手工判断：

- 收藏地点应如何排序，是否顺路；
- 营业时间、停止入场、预约和末班交通是否冲突；
- 餐厅、咖啡店、商店、厕所和休息点是否值得绕路；
- 一天的步行、站立、排队、换乘和早出晚归是否超过体力预算；
- 天气、交通、疲劳或临时意愿变化后，剩余行程如何调整；
- 信息来自哪里、是否新鲜、是事实还是估算。

## 3. 产品原则

1. 用户已选地点优先：推荐用于补全可执行行程，而不是淹没用户意图。
2. 路线感知：餐饮、购物和休息服务必须结合行程路段及 Detour Cost 排序。
3. 约束优先：时间窗、预算、预约、交通和体力由确定性规则或优化器判断。
4. LLM 有边界：负责自然语言、偏好抽取、高层决策和解释，不生成实时事实。
5. 来源可追踪：每个实用信息记录来源、抓取时间和置信等级。
6. 动态可重排：改变剩余行程时保留已完成、锁定和预约项目。
7. 高风险操作需确认：任何真实预订、实名或支付必须经过 Human-in-the-loop。

## 4. 信息可信度

TripPilot 对会影响执行的字段使用统一状态：

- `VERIFIED`：来自可追踪的权威或约定可信数据源，且仍在有效期内；
- `ESTIMATED`：通过明确算法或历史数据估算，必须展示估算依据；
- `AI_SUGGESTION`：模型提出的建议，不作为营业、价格、交通等事实。

未知值保持未知，不能以 LLM 文本补齐。动态信息（天气、拥挤、实时交通、价格和库存）与静态知识（介绍、标签、通常游览时长）分开存储并采用不同 TTL。

## 5. 核心能力域

- Preference Engine：旅行者档案、同行结构、偏好、耐受度和历史反馈。
- Retrieval Engine：收藏导入、POI/RAG 检索、候选召回和来源管理。
- Optimization Engine：时间窗、路径、预算、体力、餐时及预约约束。
- Agent Engine：Planner → Tools → Optimizer → Critic → Replanner 的受控闭环。

## 6. 关键体验

### 规划前

用户输入城市、日期、住宿位置、收藏地点、同行人、预算和旅行节奏。系统先澄清硬约束，再补充必要候选。

### 规划中

系统给出日程、交通段、预计花费和 Physical Load Score，并解释入选、落选及绕路取舍。缺少可靠信息时显式提示，而非生成看似确定的答案。

### 旅行中

用户可以表达“累了”“下雨了”“饿了”“不想去了”或“想早点回酒店”。系统只重排尚未完成的部分，展示变化、代价和约束检查结果，待用户接受后替换当前计划。

## 7. 非目标与安全边界

- Phase 0 不实现新业务功能，不切换前端框架，不引入 LangGraph。
- MVP 不承诺实时库存、真实预订或自动支付。
- 未经用户确认，Agent 不调用会创建订单、取消订单或支付的工具。
- 不将 Google Maps、Google Places 或任何单一供应商的数据结构渗透到核心领域模型。

## 8. 成功指标

后续按阶段采集 Task Success、Constraint Satisfaction、Budget Satisfaction、Time Conflict、Route Efficiency、Preference Alignment、Physical Load Satisfaction、Tool Call Success、Replanning Success、Hallucination、Latency 和 Token Cost。MVP 首先关注约束满足率、路线效率、体力预算命中率和信息可追踪率。
